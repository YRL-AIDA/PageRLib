# ADR-001: Стратегия извлечения изображений из PDF для OCR

**Дата:** 2026-07-16
**Статус:** Принято
**План:** [00001-image-extractor.md](../plan/00001-image-extractor.md)

---

## Контекст

`Images2RegionsExtractor` принимает `PageRDF` и применяет Tesseract OCR ко всем изображениям в документе. Для image-файлов (PNG, JPEG) `FileInput` возвращает `PageRDF`, где `Image`-объекты содержат пиксельный массив (`data["array"]`). Проблема возникает с PDF-документами: `FileInput` через `MinerPDFModel` возвращает `Image`-объекты только с bbox и именем файла, **без пиксельных данных**.

Возникает вопрос: как `Images2RegionsExtractor` должен получать пиксели для OCR при обработке PageRDF, полученного из PDF?

## Ключевые архитектурные принципы

Приняты два фундаментальных принципа, определяющих архитектуру экстрактора:

1. **On-demand обработка.** Экстрактор применяется пользователем явно, когда нужен OCR. Никакой автоматической активации при загрузке файла. `FileInput` возвращает документ «как есть».
2. **Независимость от источника.** Экстрактор работает с уже готовым `PageRDF`. Ему не важно, как документ был создан — через `FileInput`, `PDFIMGExtractor`, или вручную. Единственное требование: изображения, подлежащие OCR, должны иметь пиксельные данные.

## Альтернативы

| Вариант | Описание | Плюсы | Минусы |
|---------|----------|-------|--------|
| **A. Рендеринг страниц** | `pdf2image.convert_from_path()` → растеризация всей страницы → OCR всей страницы | Простота, уже есть `PDFIMGExtractor` как референс | Память на многостраничных PDF (но рендеринг постраничный), OCR дублирует уже извлечённый PDFMiner-текст |
| **B. Извлечение встроенных изображений** | PDFMiner `LTImage.stream` → декодировать пиксели → OCR каждого изображения отдельно | Точечная работа: только изображения, не дублирует текст | Не все форматы декодируются, сложность, PDFMiner может не дать stream |
| **C. Гибрид** | Рендеринг страниц как fallback + извлечение `LTImage` где возможно | Максимальное покрытие | Два пути кода, сложность поддержки |
| **D. Разделение ответственности** | Экстрактор НЕ занимается извлечением пикселей из PDF. Он обрабатывает только те Image, у которых уже есть `data["array"]`. За наполнение PageRDF пикселями отвечают другие компоненты (`FileInput`, `PDFIMGExtractor`). | Максимальная простота экстрактора, чистое разделение слоёв, соответствует архитектурным принципам | Требует дополнительного шага от пользователя для PDF (но это осознанный дизайн, а не ограничение) |

## Решение

**Принят вариант D — разделение ответственности.**

`Images2RegionsExtractor` — это **чистый OCR-экстрактор**. Он:

- Обходит все страницы `PageRDF`
- Для каждого `Image`-объекта проверяет наличие `data["array"]`
- Если пиксели есть → применяет Tesseract OCR → создаёт `Region` с текстом и confidence scores
- Если пикселей нет → **пропускает** изображение

Извлечение пикселей из PDF **не входит в зону ответственности экстрактора**. Это задача других компонентов:

| Компонент | Ответственность |
|-----------|----------------|
| `FileInput` | Загрузка документа, создание `PageRDF` «как есть». Для изображений — с пикселями, для PDF — с текстом PDFMiner и Image-bbox без пикселей |
| `PDFIMGExtractor` | Рендеринг страниц PDF как изображений (уже существует) |
| `Images2RegionsExtractor` | OCR только для Image с пиксельными данными |

### Типичные пользовательские сценарии

**Сценарий 1: изображение (PNG/JPEG)**
```
FileInput("scan.png") → PageRDF (Image с data["array"])
  → Images2RegionsExtractor.extract() → PageRDF (Image + Region с OCR-текстом)
```

**Сценарий 2: PDF с текстовым слоем + встроенные изображения**
```
FileInput("doc.pdf") → PageRDF (текст PDFMiner + Image bbox без пикселей)
  → Images2RegionsExtractor.extract() → Image без пикселей пропускаются, OCR-текста для них нет
```

**Сценарий 3: отсканированный PDF (только изображения)**
```
PDFIMGExtractor.extract("scan.pdf") → PageRDF (Image с data["array"] от рендеринга страниц)
  → Images2RegionsExtractor.extract() → PageRDF (Image + Region с OCR-текстом)
```

## Последствия

### Положительные

- **Чистая архитектура:** каждый компонент делает одно дело. `FileInput` — загрузка, `Images2RegionsExtractor` — OCR, `PDFIMGExtractor` — рендеринг.
- **Простота реализации:** экстрактору не нужно знать о внутренностях PDF, PDFMiner, или `pdf2image`.
- **Гибкость:** пользователь сам строит pipeline под свои нужды.
- **Соответствие архитектурным принципам:** экстрактор ничего не знает о происхождении PageRDF.

### Отрицательные

- Для PDF с встроенными изображениями пользователь должен явно организовать pipeline (например, `PDFIMGExtractor` → `Images2RegionsExtractor`), а не получить всё «из коробки».
- Если в будущем потребуется точечный OCR встроенных изображений PDF (без растеризации всей страницы), потребуется отдельный компонент или расширение `MinerPDFModel`.

### Требующиеся изменения

- `Images2RegionsExtractor.extract()` не содержит логики рендеринга PDF или извлечения `LTImage`.
- Метод `_render_pdf_page()` (упомянутый в плане как задача 2.6) **не реализуется**.
- `FileInput.image_reader()` упрощается: загрузка → `Image` с `data["array"]` → `PageRDF` без OCR.
