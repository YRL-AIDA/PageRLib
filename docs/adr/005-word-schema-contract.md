# ADR-005: Единый контракт схемы слова (Word)

**Дата:** 2026-10-16
**Статус:** Принято
**План:** [00002-words-schema-uniform.md](../plan/00002-words-schema-uniform.md)
**Связанные ADR:** [004-dtype-extension.md](./004-dtype-extension.md) (`Word.data["confidence"]`), [003-extractor-hierarchy.md](./003-extractor-hierarchy.md)

---

## Контекст

Два продюсера создают слова с **разными схемами** (факты сверены с кодом 2026-10-16):

| Путь | Продюсер | Файл, строки | Схема слова |
|------|----------|--------------|-------------|
| PDF | `TextExtractor._create_word` | `src/pagerlib/file_input/pdf_as_json_model/miner_pdf_model/text_extractor.py:74-87` | `{"segment", "text", "font"}`; `font` = `{"fontname", "fontsize", "is_normal"}` из первого `LTChar` (строки 51–55) |
| OCR | `Image2Words.extract_from_img` | `src/pagerlib/extractors/page_extractor/images2regions/image2words.py:71-87` | `{"text", "conf", "segment"}` — **без `font`**; `conf` = float Tesseract (0..100) |

Дрейф схем привёл к `KeyError: 'font'` в `Rows2Regions.fix_row_this_image` (`src/pagerlib/extractors/page_extractor/rows2regions/rows2regions.py:87`) — жёсткий доступ `w['data']['font']` при ручной пересборке слов.

Каноническая нормализация **уже существует и безопасна для обеих схем** — `Row._get_children_from_dict_list` (`src/pagerlib/dtypes/physical_elements/row.py:18-30`):

- `data = word_json["data"] if "data" in word_json else {"text": word_json["text"]}` — поддерживает и вложенную схему `{"segment", "data"}` (вывод `Word.to_dict()`), и плоскую `{"text", "font", "conf"}`;
- `font` добавляется в `data` только `if "font" in word_json`;
- `conf` → `data["confidence"]` только `if "conf" in word_json`.

Потребители `font` (проверено по коду):

- `_HeadingInfo._extract_font` (`src/pagerlib/extractors/document_extractor/logical_structure_extractor.py:30-46`) — читает `word.data["font"]` только `if "font" in word.data`, иначе конструирует `Font({})` (дефолт `size=-1`, `width=0.5`, `italic=0.0`; `_HeadingInfo` маппит `size=-1` → `12.0`).
- Токенизаторы (`rowsGLAM_tokenizer.py`) — **не читают** font-метаданные слова: текст через `w.get('data').get('text', '')` (строки 128, 195); шрифтовой признак строки берётся из **пиксельного патча** строки (`FontEmbRowGLAMTokenizer.get_vec_font`, 303–308) с защитой `_get_vec_font_safe` (275–280, `try/except → нули`).
- `Word.confidence` (`src/pagerlib/dtypes/physical_elements/word.py:19-21`) — производится OCR, хранится, больше нигде не потребляется.

**Находка при верификации (расхождение с планом этапа):** `Font({})` **падает** с `KeyError: 'fontname'`. В `font.py` (`set_width`, строка 25; `set_italic`, строка 35) выполняется жёсткий доступ `dict_font['fontname'].lower()` без проверки наличия ключа: при пустом словаре ветки `'width'`/`'is_bold'` не срабатывают, и происходит обращение к несуществующему ключу. Значит, ветка `_extract_font`, возвращающая `Font({})` для OCR-слов (без `font`), сейчас крашится. Это **второй** дефект жёсткого доступа (после `rows2regions.py:87`), который обязан быть устранён, чтобы контракт «отсутствие `font` для OCR» был безопасен для всех потребителей.

## Альтернативы

### Вариант A. Отсутствие ключа (продюсеры эмитят только свои поля)

Каноническая схема `Word.data`: `text` — обязательно; `font` — опционально, только PDF; `confidence` — опционально, только OCR. Продюсеры не «выравнивают» схему: OCR не создаёт `font`, PDF не создаёт `confidence`. Единая точка нормализации — `Row._get_children_from_dict_list`.

### Вариант B. Пустой `{}` для отсутствующих полей

Продюсеры выравнивают схему на выходе: OCR добавляет `"font": {}` в каждое слово. Набор ключей на входе конвейера одинаков для обоих путей.

### Вариант C. Полное выравнивание с дефолтами (`font: {}`, `confidence: None`)

Каждый продюсер эмитит обе опциональные компоненты с нейтральными значениями-заглушками.

## Сравнительный анализ

| Критерий | A. Отсутствие ключа | B. Пустой `{}` | C. Полное выравнивание |
|----------|--------------------|----------------|------------------------|
| Честность данных | ✅ `font` создаётся только там, где физически существует (PDF) | ⚠️ `font: {}` создаётся искусственно для OCR | ❌ `font: {}` + `confidence: None` выдумываются |
| Безопасность потребителей | Требует безопасного доступа (`.get()` / `"key" in dict`) — уже принятый стиль кода; плюс починка `Font({})` | `{}` — валидный dict, но требуется та же починка `Font({})` | `None`/`{}` вводят дополнительную семантику для каждого потребителя |
| Соответствие текущему коду | ✅ Ровно то, что уже делает `Row._get_children_from_dict_list` и `_extract_font` | ⚠️ Изменение OCR-продюсера (`image2words.py`) | ❌ Изменение обоих продюсеров и всех потребителей |
| Риск регрессии PDF | Низкий — PDF-поведение не меняется | Низкий | Средний — меняется схема, доходящая до потребителей |
| Сохранность `confidence` | ✅ Не теряется (нет ручной пересборки в `rows2regions`) | ⚠️ Риск потери при пересборке слов | ✅ Сохраняется ценой мусорных полей |
| Стоимость | Только фиксы жёстких доступов | Фикс OCR-продюсера + фиксы жёстких доступов | Максимальная |

## Рекомендация

**Вариант A.** Каноническая схема `Word.data`:

- `text: str` — **обязательно** (оба продюсера);
- `font: Dict` — **опционально, только PDF** (`TextExtractor`); для OCR ключ **отсутствует**;
- `confidence: float` — **опционально, только OCR** (`Image2Words`, значение 0..100 из Tesseract `conf`); для PDF ключ **отсутствует**.

Сопутствующие решения:

1. **Единая точка нормализации** — `Row._get_children_from_dict_list`. Продюсеры эмитят только свои поля и схему не «выравнивают»; любое слово, проходящее через `Row.from_dict`, приводится к каноническому виду именно здесь.
2. **Дилемма «пустой `{}` vs отсутствие ключа»:** для OCR `font` физически не существует → ключ **отсутствует**. Пустой `{}` допустим только там, где поле реально нужно для записи/чтения контракта (например, `Font({})` как дефолт `_extract_font` — после починки).
3. **Запрет жёсткого доступа** `dict["key"]` к опциональным полям слова у потребителей; разрешён только `.get()` / `"key" in dict`.
4. **Обязательная починка дефекта `Font({})`:** в `font.py` `set_width`/`set_italic` должны использовать безопасный доступ к `fontname` (`.get('fontname', '')` или проверка `"fontname" in dict_font`) — иначе ветка «шрифт отсутствует» (`Font({})`) крашится, и OCR-страницы падают в `LogicalStructureExtractor`.

## Последствия

### Положительные

- Единый конвейер `Rows2Regions` / `LogicalStructureExtractor` работает и на PDF-, и на OCR-словах без краха.
- Для OCR `font` не выдумывается (требование «не врать в данные»); реальный `font` PDF сохраняется для определения заголовков.
- `Word.confidence` для OCR-слов сохраняется на всём пути (при выборе варианта A фикса `rows2regions`).
- Точка нормализации одна — новые продюсеры слов обязаны только эмитить свои поля.

### Отрицательные

- Потребители обязаны всегда использовать безопасный доступ к опциональным полям — это дисциплина разработки, а не гарантия на уровне типов.
- `Word.data` остаётся неструктурированным контейнером: отсутствие схемы времени исполнения для `font`/`confidence` (компромисс гибкости, заложенный в ADR-004).

### Требующиеся изменения (выполняет coder в рамках этапа 00002)

1. `rows2regions.py:84-91` — убрать ручную пересборку слов (вариант A по плану этапа): `fix_row_this_image` не должен читать `w['data']['font']`.
2. `font.py:25,35` — заменить `dict_font['fontname']` на безопасный доступ (`.get('fontname', '')`).
3. Регрессионные тесты секции 3 плана: OCR-слова без `font` (включая `_extract_font`), PDF-слова с `font`, смешанный случай.
